
================================================================================
TRACCIA PROGETTO — Tongue (chatbot news + LLM)
Riferimento: consegna.txt. Allineata a corso/Tutor: persistenza e sessione da DB; per la chat,
  un solo POST /api/chat (dettaglio PF4).
================================================================================

---0. CONSEGNA (sintesi vincoli) ---
- Chatbot che riassume notizie da testate tramite API esterne (cascata ibrida multi-provider — PF1, PS2).
- Input: DATA + messaggio in linguaggio naturale (allineato a consegna.txt: nessun orario/fascia
  oraria obbligatoria — vedi PF4 / PS2 per filtro sul solo giorno di calendario).
- Front: singolo input-box (textarea, bottone, risultato in pagina).
- Back: un solo endpoint che riceve testo + data (flusso chat); recupera articoli; chiama LLM
  (system prompt + articoli + messaggio + storico da DB); risposta al client; lettura/scrittura DB
  nello stesso handler (vedi PF4).
- Persistenza conversazione (storico recuperabile nello stesso POST — vedi PF3, PF4, PS1 Prisma).
- Deploy gratuito (coerente con Netlify / Firebase / Render nella consegna).
- System prompt: news analyst Tongue, tono giornalistico, no opinioni, no invenzioni,
  ammettere dati insufficienti, 3–5 paragrafi; lingua risposta IT di default, altra lingua se
  richiesta esplicitamente in chat (Fase 5).

Allineamento consegna / Tutor: nessun secondo endpoint HTTP per la chat (niente GET /messages).
  Dopo refresh: POST con action loadHistory. Dopo ogni turno chat: risposta con `messages` completo
  (fonte di verità UI — PF4). Testo e data obbligatori solo in modalità chat, non in loadHistory (PF4).

---0.bis OBIETTIVO PRODOTTO — VERIFICABILITÀ (requisito di progetto) ---
- **Scopo UX:** l’utente finale (anche non programmatore) deve poter controllare l’affidabilità del
  sistema in modo diretto: oltre al **riassunto**, l’interfaccia mostra in modo chiaro i **link agli
  articoli** da cui il riassunto del turno è tratto (o su cui è ancorato). L’utente deve poter
  ragionare: «questi link sono pertinenti alla mia richiesta» e «i fatti salienti del riassunto
  corrispondono a ciò che dicono le fonti che mi avete mostrato».
- **Coerenza backend:** il server non deve presentare come “fonti del riassunto” un elenco diverso da
  quello su cui il modello ha effettivamente basato la sintesi per quel turno. In pratica: dopo il
  fetch grezzo dalle API (cascata PS2), serve uno **step esplicito di selezione / ordinamento della
  rilevanza** (vedi PF8: LLM selettore *oppure* rerank con embedding — scelta di implementazione)
  così che l’array `articles` persistito nel `metadata` del messaggio ASSISTANT (PS1) e mostrato in UI
  sia **allineato** alle esigenze dell’utente e al contenuto del `reply`, non un semplice dump dei
  primi risultati del provider. Se nessun articolo supera la soglia di pertinenza, il sistema deve
  ammetterlo (reply + elenco vuoto o messaggio chiaro), non riempire con link fuori tema.
- **Nota:** resta vero che non si introduce un secondo endpoint HTTP dedicato alle sole fonti: il
  contratto resta `messages[].metadata` (PF4) come canale di verità per titolo, URL, testata, ecc.

PARTE I — PUNTI FERMI

PF1. Stack
- Front: Next.js, TypeScript, Tailwind CSS (unico sistema di stili); Axios per le chiamate HTTP
  al backend (solo POST /api/chat — vedi PF4).
- Back: Express, TypeScript, Node.js.
- LLM: OpenAI, SDK npm "openai" (niente LangChain).
- DB: PostgreSQL su Supabase, ORM Prisma.
- Articoli: **cascata ibrida** su **2–3 API news generaliste** (ordine configurabile — PS2), non una
  singola testata. Obiettivo: aderenza alla consegna («varie testate» via aggregatori), copertura e
  meno rischio di restare senza quota in un giorno di sviluppo.
- Lingua: **codice** (identificatori, struttura) in **inglese**; **testi UX** (etichette, errori
  mostrati all’utente, placeholder) in **italiano** di default. **Risposte del modello** in **italiano**
  di default; se l’utente chiede esplicitamente in chat una lingua diversa (es. «rispondi in inglese»,
  «answer in English»), il system prompt impone di usare quella lingua per il turno / i turni
  successivi fino a nuova richiesta (Fase 5).
- Auth: non richiesta; sessione anonima tramite sessionId (UUID).

PF2. Repository
- Monorepo: un solo repository Git.
- Cartelle: web/ (Next), server/ (Express + cartella prisma/).
- Due package.json indipendenti (niente workspace obbligatorio all’inizio).

PF3. Comportamento conversazione (decisione finale)
- sessionId: UUID, generato dal server al primo POST senza sessionId; salvato in
  localStorage (chiave es. tongue_session_id); inviato nel body dei POST successivi.
- New chat: pulsante che elimina sessionId dal localStorage e azzera la UI; al prossimo POST
  si ottiene una nuova Conversation (nuovo id). Nessuna memoria incrociata tra sessioni diverse.
- Intra-sessione (stesso sessionId):
  - Ogni turno: salvare in DB messaggio USER e messaggio ASSISTANT.
  - Prima di chiamare OpenAI: caricare da DB solo gli ultimi 10 turni della sessione
    (un turno = messaggio USER + messaggio ASSISTANT → al massimo 20 messaggi), ordine
    cronologico, e includerli nel prompt insieme al nuovo messaggio utente del turno corrente.
    (Motivo: tetto token; lo storico completo resta nel DB e nella risposta POST /api/chat — vedi PF4.)
  - Ordine consigliato per turno: persistere messaggio USER; costruire prompt OpenAI con ultimi 10
    turni da DB (include già il messaggio USER appena salvato) + contesto articoli se applicabile;
    chiamare OpenAI; persistere messaggio ASSISTANT.
  - Fonti notizie — refetch provider vs riuso metadata (stessa logica del pattern bundle + follow-up):
    - Bundle: sull’ultimo messaggio ASSISTANT che ha eseguito un fetch news, in metadata restano
      `date`, elenco articoli normalizzati (titolo, URL, abstract troncati, opz. `source` /
      `providerId` — PS1/PS2). Per il prossimo turno: ultimo bundle scorrendo ASSISTANT dal più
      recente al passato.
    - Riuso (nessun nuovo fetch): se esiste un bundle e il body del POST ha la stessa `date` e
      `refreshNews` è assente o false. Il nuovo `message` va solo al LLM come follow-up; non si usa
      come nuova query verso le API news.
    - Nuovo fetch: primo turno con notizie dopo New chat; oppure nessun bundle disponibile;
      oppure `date` non coincide col bundle; oppure `refreshNews: true` (stesso giorno ma nuova
      ricerca articoli — es. checkbox in UI).
    - Non usare il solo fatto che `message` sia cambiato per forzare il refetch (altrimenti ogni
      follow-up richiamerebbe le API).
- Dopo refresh / riapertura (stesso browser, sessionId ancora in localStorage):
  - All’avvio la UI chiama POST /api/chat con action loadHistory (solo sessionId) e ridisegna i
    messaggi dalla risposta; il POST chat successivo continua la stessa sessione con memoria coerente.
- Timeout sessione lato server: non richiesto dalla consegna (opzionale in futuro).

PF4. API HTTP
- Un solo endpoint per la chat: POST /api/chat (allineato alla consegna: nessun GET separato).
  Due “modalità” tramite campo opzionale `action` nel body JSON (stesso path, stesso metodo).

  (A) action assente o "chat" — turno conversazione (default).
  Body: {
    "action": "chat" | omesso,
    "date": "YYYY-MM-DD",
    "message": "string",
    "sessionId": "string opzionale",
    "refreshNews": "boolean opzionale (default false) — se true, nuovo fetch news (cascata PS2) con il
      message corrente come q anche se la data coincide col bundle (nuovo argomento stesso giorno)"
  }
  Flusso server: validazione → (eventuale fetch news per PF3 — PS2) → lettura ultimi turni da DB per
  prompt LLM → OpenAI → persistenza USER + ASSISTANT → risposta JSON.
  Nessun campo articlesUsed (o simile): quali articoli usare decide solo il server (PF3 + metadata).
  Finestra notizie (PS2): giorno di calendario `date` confrontato con la data di pubblicazione degli
  articoli (implementazione di riferimento: giorno in UTC); opzionale fallback “lento” su articoli
  recenti se il filtro stretto non trova match (vedi env NEWS_STRICT_CALENDAR_WINDOW nel codice).
  Risposta 200: {
    "reply": "string",
    "sessionId": "string",
    "messages": [ … ]
  }
  Decisione chiusa: in ogni risposta in modalità chat il server include sempre `messages`, cioè lo
  storico completo della conversazione ordinato per createdAt crescente (shape PS1: id, role, content,
  createdAt, metadata). Il front imposta la lista messaggi da `response.messages` (niente fork
  “solo reply + append locale”). Per conversazioni molto lunghe in produzione si potrebbe introdurre
  paginazione in una revisione futura; per il perimetro corso lo storico completo è accettabile.

  (B) action "loadHistory" — sola lettura DB per ricostruire la UI dopo refresh (niente fetch news, niente LLM).
  Body: { "action": "loadHistory", "sessionId": "uuid" }
  Risposta 200: { "sessionId": "string", "messages": [ … ] } — nessun campo `reply`.
  Validazione sessionId UUID; 404 se nessuna Conversation con quell’id (stesso spirito PS4).
  Interpretazione consegna («riceve testo e data»): si riferisce al flusso di sintesi news (modalità
  chat). loadHistory è sempre lo stesso URL/metodo ma non è un turno di chat: non richiede testo/data;
  così si rispetta «un solo endpoint» senza introdurre GET dedicati.

  Ogni elemento in `messages`: { "id": "uuid", "role": "USER" | "ASSISTANT", "content": "string",
  "createdAt": "ISO-8601", "metadata": null | object } — metadata come persistito (fonti/link articoli
  su ASSISTANT); tipicamente null su USER.

- URL base: NEXT_PUBLIC_API_URL senza slash finale; path completo .../api/chat
- Probe / health (es. GET /health): solo se imposto dall’hosting (Render ecc.); non fa parte del
  contratto funzionale del chatbot né sostituisce loadHistory; non usare per lo storico conversazione.

PF6. Variabili d’ambiente
- web/.env.example: NEXT_PUBLIC_API_URL
- server/.env.example: DATABASE_URL, OPENAI_API_KEY, PORT, CORS_ORIGIN;
  chiavi provider (solo quelle in uso; le assenti → provider saltato in cascata): es.
  NEWSDATA_API_KEY, THENEWS_API_KEY, GNEWS_API_KEY — vedi PS2 per ordine e nomi stabili;
  opz. DIRECT_URL (solo se DATABASE_URL è pooled — vedi Parte III Supabase).
- (opz.) OPENAI_MODEL
- (opz.) NEWS_PROVIDER_ORDER — lista separata da virgole (es. newsdata,thenewsapi,gnews);
  default sensato in codice se assente.
- (opz.) NEWS_TARGET_RELEVANT_ARTICLES (default **4**) — soglia di **stop cascata**: con almeno 4
  articoli **inerenti** (PF8) cumulativi non si chiama il provider successivo (salvo il caso |inerenti| > 8,
  vedi PS2: si applica il cap a 8 e stop).
- (opz.) MAX_ARTICLES_FOR_PROMPT (default **8**) — **massimo** di articoli **inerenti** passati al LLM
  di sintesi e persistiti in `metadata.articles`; **minimo 1** articolo inerente per procedere al
  riassunto (se dopo tutti i provider gli inerenti sono **0**, niente sintesi — messaggio all’utente).
- (opz.) NEWS_SELECTOR_POOL_MAX — tetto candidati **grezzi** cumulativi numerati per il selettore (PF8).
- Chiavi segrete mai nel bundle Next.

PF7. Qualità, uniformità del codice e TypeScript
- Stile di coding **uniforme** su tutto il monorepo (`web/` e `server/`): stesse convenzioni su naming,
  struttura dei moduli, formattazione (Prettier/ESLint se presenti), pattern per errori/async e per le
  chiamate HTTP — così il progetto non sembra scritto da più persone senza coordinamento né mal
  pianificato.
- Evitare file con **troppe funzioni** o troppe responsabilità nello stesso modulo: preferire file più
  piccoli e coesi, estrarre servizi/helper quando un file cresce; obiettivo: leggibilità e manutenzione
  senza “god file”.
- **TypeScript**: codice tipizzato in modo corretto e coerente con le **best practice** (evitare `any`
  non motivato; usare tipi espliciti per boundary API/DTO; rispettare `strict` del `tsconfig` del
  package; gestione errori e nullability chiara). Allineamento continuo a ESLint/TypeScript del repo.

PF8. Selezione rilevanza articoli (obiettivo 0.bis — implementazione obbligatoria)
- **Definizione (decisione progetto):** articolo **inerente** = notizia che **tratta l’argomento**
  richiesto dall’utente (`message`). Richiesta **generale** (es. notizie del giorno senza tema stretto):
  si considerano inerenti le notizie **più rilevanti** rispetto a quella richiesta, con lo **stesso**
  criterio usato per i temi specifici (il selettore interpreta «generale» vs «specifico» in modo esplicito
  nel prompt).
- **Cascata incrementale + selettore (implementazione Tongue):** non si decide la pertinenza sul solo
  conteggio grezzo. Dopo ogni fetch provider: merge in pool cumulativo **dedup URL**, filtro finestra
  calendario su `date`, poi **selettore** (es. LLM) sull’elenco **numerato** di candidati in finestra
  (fino a `NEWS_SELECTOR_POOL_MAX`) che produce l’insieme **inerenti** (solo URL tra i candidati).
- **Regola unica tra provider:** il criterio con cui si marca «inerente» e con cui si scelgono le
  **«migliori 8»** quando gli inerenti sono **> 8** deve essere **lo stesso** per tutti i provider
  (stesso prompt / stesso scoring su lista unificata), così NewsData, TheNewsAPI e GNews sono solo
  **sorgenti di candidati**, non logiche di ranking diverse.
- **Soglie numeriche (allineate a PS2):** `NEWS_TARGET_RELEVANT_ARTICLES` default **4** (basta così per
  non chiamare il provider successivo, se non si è già nel caso «>8 inerenti» che impone cap e stop);
  `MAX_ARTICLES_FOR_PROMPT` default **8** (tetto in input alla sintesi e in `metadata.articles`);
  **minimo 1** inerente per la sintesi — con **0** inerenti dopo tutti i provider, risposta che lo spiega,
  **nessuna** invenzione di fatti o fonti.
- Il prompt di sintesi finale usa **solo** gli articoli inerenti selezionati per quel turno;
  `metadata.articles` coincide con quell’insieme (cardinalità tra 1 e 8 quando c’è sintesi).
- **Alternativa documentata (non usata in Tongue):** rerank con embedding al posto del selettore LLM;
  differenza: similarità vettoriale vs ragionamento esplicito; costi e vincoli di validazione diversi.
- Vincoli comuni: niente articoli inventati; solo URL già presenti tra i candidati del fetch;
  messaggi d’errore lato utente in italiano se il passo fallisce; test in Fase 7 su pertinenza
  percepita e su **zero inerenti**.

PARTE II — DETTAGLI IMPLEMENTAZIONE (checklist)

--- PS1. Prisma (schema) ---
- Conversation: id UUID, createdAt, updatedAt (touch su ogni nuovo messaggio).
- Message: id, conversationId FK (onDelete Cascade), role USER|ASSISTANT, content Text,
  createdAt, metadata Json? — in metadata per il turno “notizie”: `date` richiesta, array articoli
  { title, url, abstract (troncato), opz. source, providerId } che rappresentano le **fonti
  verificabili** mostrate all’utente per quel turno (allineate al riassunto dopo PF8 — obiettivo 0.bis);
  utile per follow-up senza rifetch (PF3).
- Persistenza: ogni POST /api/chat in modalità chat che completa un turno salva sempre due righe in
  ordine cronologico — una USER (messaggio ricevuto) e una ASSISTANT (risposta generata). Tutta la
  conversazione resta nel DB; il tetto “ultimi 10 turni” (PF3) riguarda solo cosa si manda al LLM,
  non cosa si persiste; il campo `messages` nelle risposte POST (chat e loadHistory) espone sempre
  l’intero thread persistito.
- Indice: (conversationId, createdAt).
- Serializzazione in uscita (PF4): stessi campi sopra incluso metadata senza strip (niente segreti
  nel shape previsto; solo titoli/URL/estratti e attribuzione fonte come da provider).
- Conversation.id = sessionId (UUID generato dal server al primo POST, PF3): niente default su id;
  il client riusa lo stesso id nelle richieste successive.

Schema di riferimento (server/prisma/schema.prisma — adattare solo se necessario):

  generator client {
    provider = "prisma-client-js"
  }

  datasource db {
    provider = "postgresql"
    url      = env("DATABASE_URL")
  }

  enum MessageRole {
    USER
    ASSISTANT
  }

  model Conversation {
    id        String    @id @db.Uuid
    createdAt DateTime  @default(now())
    updatedAt DateTime  @updatedAt
    messages  Message[]
  }

  model Message {
    id             String       @id @default(uuid()) @db.Uuid
    conversationId String       @db.Uuid
    conversation   Conversation @relation(fields: [conversationId], references: [id], onDelete: Cascade)
    role           MessageRole
    content        String       @db.Text
    metadata       Json?
    createdAt      DateTime     @default(now())

    @@index([conversationId, createdAt])
  }

Azione:
- Copiare lo schema nel repo; `npx prisma migrate dev --name init` in locale (genera cartella
  migrations); in produzione `npx prisma migrate deploy` (vedi nodo Render / PS6). Se usi pooler
  Supabase, aggiungere directUrl in datasource come in Parte III.

--- PS2. API news — cascata ibrida (multi-provider) ---

Obiettivo
- Allineamento consegna: più testate tramite **aggregatori**; meno rischio di “giornata a secco” in dev
  rispetto a un solo provider o a una singola testata.

Modello dati interno (normalizzazione)
- Ogni adapter mappa la risposta del provider in `NormalizedArticle`: almeno `title`, `url`,
  `publishedAt` (ISO o Date), `excerpt` (description/abstract/snippet concatenati e troncati),
  opz. `sourceName`, `providerId` (stringa stabile: newsdata | thenewsapi | gnews | …).
- Tutta la cascata e il prompt LLM lavorano solo su `NormalizedArticle[]` dopo dedup.

Ordine e configurazione
- Ordine fisso di priorità: env `NEWS_PROVIDER_ORDER` (virgole), es. `newsdata,thenewsapi,gnews`.
  Provider senza chiave in `.env` → **saltato** (non errore fatale se almeno un altro è configurato).
- Costanti (override via env): `NEWS_TARGET_RELEVANT_ARTICLES` (default **4**, stop cascata),
  `MAX_ARTICLES_FOR_PROMPT` (default **8**, tetto inerenti per sintesi/metadata), `NEWS_SELECTOR_POOL_MAX`
  (candidati grezzi cumulativi numerati al selettore), timeout HTTP per chiamata provider (es. 10–15s).
  **Minimo sintesi:** **1** articolo **inerente** (PF8); con **0** inerenti dopo tutti i provider ⇒ niente
  riassunto, solo messaggio all’utente.

Cascata ibrida incrementale (decisione chiusa — allineata a PF8)
Notazione: dopo ogni passaggio provider, `I` = numero di articoli **inerenti** sul pool cumulativo
(dopo dedup URL, filtro calendario, selettore — vedi PF8). Soglia stop `T` = `NEWS_TARGET_RELEVANT_ARTICLES`
(default 4). Tetto `M` = `MAX_ARTICLES_FOR_PROMPT` (default 8).

1. `acc` = [] (candidati grezzi normalizzati). Per ogni provider nell’ordine (con chiave configurata):
   - Fetch adapter (`message`, `date`, …); merge in `acc` con dedup; tetto `NEWS_SELECTOR_POOL_MAX` su `acc`
     dove applicabile; filtro finestra calendario su `date` vs `publishedAt` (e fallback “lento” se da env).
   - Selettore su elenco numerato in finestra → insieme **inerenti**, |I| aggiornato.
   - **Caso 1:** se |I| **>** M → rank con **criterio unico** (PF8), tenere le **M migliori**, **stop cascata**
     → sintesi.
   - **Caso 2:** se **T ≤ |I| ≤ M** → **stop cascata** → sintesi su tutti gli |I| inerenti (**include |I| = 8**).
   - **Caso 3:** se **|I| < T** dopo questo provider e resta almeno un provider in coda → **continua**
     al provider successivo (si mantengono gli inerenti già trovati; il merge dei nuovi grezzi aggiorna `acc`
     e il selettore rivaluta sul cumulativo).
   - **Caso 3A (dopo il secondo provider):** se |I| **≥ T** e |I| ≤ M → sintesi; se |I| **>** M → **M migliori**
     → sintesi; se |I| **< T** e c’è il terzo provider → continua.
   - **Caso 3B (dopo il terzo provider, o dopo l’ultimo disponibile):** se |I| **= 0** → **nessuna sintesi**,
     messaggio che lo spiega; se **1 ≤ |I| ≤ M** → sintesi; se |I| **>** M → **M migliori** → sintesi.

2. Prompt di **sintesi** LLM: **solo** gli articoli inerenti scelti per il turno (1…M); `metadata.articles`
   allineato; excerpt coerenti con PS1 / PF3.

3. Zero **inerenti** dopo tutti i provider tentati: reply che lo spiega; non inventare fatti.

4. Nessuna chiave provider configurata (tutti assenti) su richiesta che richiede fetch: 503 o 400
   (non chiamare LLM con articoli inventati).

Adattatori (implementazione)
- Un modulo per provider (es. `services/news/providers/newsdata.ts`, …) che espone
  `fetchArticles(params): Promise<NormalizedArticle[]>` e traduce errori quota in errore tipizzato.
- README (Fase 1): tabella provider usati, link **documentazione ufficiale** e **ToS** per ciascuno,
  limiti free tier noti (ritardi 12h/24h, punti/giorno, attribuzione se richiesta — es. GNews / gnews.io),
  attribuzione in UI dove si mostrano titoli/URL.

Note operative
- **Dev**: opzionale `USE_MOCK_NEWS=true` + fixture JSON per non bruciare quota durante hot reload
  (PS7 spirito anti-spreco).

--- PS3. OpenAI (default) ---
- model consigliato (buon rapporto qualità / costo e meno errori su riassunti e istruzioni):
  gpt-4o-mini | temperature: 0.3 | max_tokens: 1200
- Override opzionale: OPENAI_MODEL in env se in futuro si cambia modello; finché assente usare il
  default sopra.

--- PS4. Validazione ed errori ---
- Modalità chat (action assente o "chat"): date obbligatoria YYYY-MM-DD; message obbligatorio, max
  4000 caratteri (default).
- Modalità loadHistory: action esattamente "loadHistory"; sessionId obbligatorio (assente o vuoto →
  400); non richiedere date/message (nessun LLM / nessun fetch news in questa richiesta).
- sessionId in modalità chat: opzionale (primo turno senza id); se presente — formato non UUID → 400;
  UUID valido ma nessuna Conversation con quell’id → 404.
- sessionId in loadHistory: obbligatorio — formato non UUID → 400; UUID valido ma nessuna
  Conversation → 404.
- action: se presente deve essere "chat" o "loadHistory"; altri valori → 400.
- refreshNews: opzionale, boolean; se assente si tratta come false.
- Errori: JSON { "error": "..." } e status HTTP coerenti (dettaglio UX lato web: PS7).

--- PS5. CORS ---
- Produzione: CORS_ORIGIN = URL canonico del front Vercel (es. https://tongue.vercel.app).
  Consigliato consentire anche le preview deploy: origini https://*.vercel.app (pattern o lista di
  stringhe nel middleware CORS Express, a seconda della libreria usata).
- Dev: http://localhost:3000 (o la porta Next effettiva); non usare wildcard * in produzione.

--- PS6. Render (Web Service, root cartella server/) ---
- Nel dashboard Render: tipo Web Service, repo collegato, Root Directory server (monorepo).
  Runtime Node; DATABASE_URL e le altre env (PF6 / Parte V) configurate sul servizio.
- Build Command (ordine consigliato): install dipendenze → client Prisma → migrazioni su Supabase
  → compilazione TypeScript se presente. Esempio:
  npm ci && npx prisma generate && npx prisma migrate deploy && npm run build
  Se il progetto non ha ancora uno script build, usare solo i tre passi Prisma + npm ci finché
  lo script non esiste; oppure build = tsc che emette in dist/.
- Start Command: npm start — deve avviare l’Express su process.env.PORT (Render imposta PORT).
- package.json (server): prevedere almeno "start": "node dist/index.js" (o equivalente dopo tsc)
  e "build": "tsc" quando si compila da TS; README ripete Build/Start per copia-incolla su Render.
- Le migrazioni devono essere committate in server/prisma/migrations; migrate deploy in
  build applica lo schema al DB di produzione (il DB deve essere raggiungibile durante il build).
- Cold start: primo request dopo idle può tardare; citato in Fase 6.

--- PS7. Qualità: anti “vibe coding”, error handling, caricamenti (UX fluida) ---

Errori tipici da evitare (checklist implementazione):
- Segreti committati o esposti al client (chiavi solo server; .env mai in Git; NEXT_PUBLIC_* solo
  per URL pubbliche).
- Validazione solo sul front: il backend deve sempre validare (PS4) e non fidarsi del client.
- CORS troppo permissivo in produzione (wildcard * o origini non necessarie).
- Stile incoerente tra file (pattern React diversi, API client duplicato): mantenere un modulo Axios
  centralizzato (baseURL da NEXT_PUBLIC_API_URL, timeout ragionevole).
- catch vuoti o solo console.log: l’utente deve vedere un feedback chiaro; in dev ok log strutturato.
- Tipi any ovunque: definire tipi per body POST (action chat vs loadHistory), risposta chat (reply +
  sessionId + messages) e loadHistory (sessionId + messages), error payload { error: string }.
- Gestione stati dimenticata (loading / errore / successo) su ogni azione async.
- Fetch API senza loader / fallback visibile: la UI resta “ferma” e poi salta — effetto scattoso e
  utente che non sa se deve aspettare (requisito esplicito sotto).
- Tutto il JS o tutte le rotte caricate subito senza code-splitting dove ha senso: bundle iniziale
  più lento del necessario (requisito lazy / dynamic sotto).
- Dipendenze aggiunte e mai usate; versioni non documentate nel README.
- Deploy senza provare env mancanti (Render/Vercel) e cold start backend.
- “God file” / pagina unica ingestibile: migliaia di righe o tutta l’app in un solo file perché
  l’AI ha incollato lì tutto il flusso — difficile da leggere, testare e correggere.

Organizzazione file e modularità (obiettivo: manutenibilità):
- Evitare di concentrare troppa logica in un solo file: spezzare per responsabilità (componenti UI,
  client API, tipi, hook, utilità) senza esagerare nel micro-file.
- web/ (Next): es. `components/` (ChatForm, MessageList, …), `lib/api.ts` o `lib/api/` (Axios),
  `types/` per DTO condivisi con il contratto PF4; eventuali `hooks/` per useChat o load storico.
  La `page` (o layout) resta sottile: composizione e wiring, non tutta la business logic inline.
- server/ (Express): es. `routes/` o `routes/chat.ts`, servizi dedicati (cascata news / provider,
  OpenAI, messaggi DB), validazione input separata se utile; `app.ts` o `index.ts` solo bootstrap e mount
  route.
- Criterio pratico: se un file supera circa ~200–300 righe o mescola molte responsabilità non
  correlate, è segnale per estrarre moduli (soglia indicativa, non dogma).

Error handling — backend (Express):
- Risposte errore sempre JSON { "error": "messaggio leggibile" } con status HTTP coerente (400, 404,
  429, 500, ecc.); messaggi `error` in **italiano** per coerenza con l’UX (salvo messaggi tecnici solo
  in log); non lasciare stack trace al client in produzione.
- Errori provider news / OpenAI / DB: messaggio generico all’utente, dettaglio solo in log server (senza
  segreti).
- Timeout e rate limit news: mappare a 502/503 o messaggio comprensibile; in cascata, il fallimento di
  un provider non deve bloccare gli altri se ne resta almeno uno valido (PS2).

Error handling — frontend (Next + Axios):
- Intercettare errori Axios: se response.data.error usarlo (o tradurre in italiano se il backend
  restituisce messaggi generici in inglese); se rete / timeout messaggio dedicato in **italiano** per
  l’utente (es. «Impossibile contattare il server», timeout).
- 404 su loadHistory o POST chat con sessionId sconosciuto (PS4): azzerare sessione locale e mostrare
  messaggio + invito a nuova chat.
- Mostrare errori in zona dedicata (banner o sotto il form), non solo alert nativi se evitabile.
- Durante errore: sbloccare la UI (non lasciare loading infinito).

Caricamenti e fluidità (evitare effetti “scattosi”):
- Obbligo: durante ogni chiamata Axios che alimenta contenuto visibile (POST loadHistory al mount se
  c’è sessionId in localStorage, POST chat a ogni invio, eventuali altre API) mostrare sempre un
  feedback di attesa — loader, skeleton o stato “Loading…” nell’area interessata — così l’utente sa
  che deve aspettare e non vede salti a vuoto.
- Stati loading distinti dove serve: es. isLoadingHistory al mount (loadHistory) vs isSending al POST
  chat — evitare un solo flag globale che nasconde tutta la pagina a ogni azione.
- Al mount: se si ripristina sessione, chiamare loadHistory con loader dedicato; non svuotare
  bruscamente il layout — area messaggi con altezza minima o skeleton leggero finché arrivano i dati;
  evitare salti verticali (CLS).
- Invio messaggio: disabilitare bottone e textarea durante la richiesta; indicatore discreto
  (spinner inline o testo “Sending…”) senza nascondere la lista messaggi esistente.
- Dopo POST chat con successo: allineare la UI a `response.messages` (lista completa). Evitare stato
  locale disallineato dal DB. Scroll: preferire smooth verso l’ultimo messaggio senza salti bruschi.
- Code-splitting / lazy (buona pratica, evitare “tutto in bundle iniziale”): in Next.js preferire
  `next/dynamic` con fallback (e dove serve `Suspense`) per componenti o sotto-alberi non necessari
  al primo paint; in Client Components si può usare `React.lazy` + `Suspense` con lo stesso obiettivo.
  Se esistono più rotte/pagine, caricare il codice della rotta (o sezioni pesanti) in modo differito
  così il primo caricamento resta leggero. Scegliere fallback coerenti (stesso stile dei loader sopra)
  per non introdurre nuovi scatti.
- Transizioni CSS: preferire brevi (opacity / height controllata) evitando animazioni lunghe su tutta
  la pagina.
- Primo avvio con backend cold (Render): prevedere primo request più lento — messaggio o timeout Axios
  adeguato (es. 60s solo se necessario) per non fallire subito.

PARTE III — Riferimenti e decisioni già chiuse (README / Supabase / fonti news)
================================================================================
- **Multi-provider (default PS2):** nel README, sezione “Fonti notizie” con elenco provider effettivi,
  link a documentazione e **Terms** di ciascuno, limiti del piano usato (free: ritardi, quote; per GNews
  verificare gnews.io), e regola di attribuzione:
  mostrare il **nome della fonte** (testata / `sourceName`) e l’**URL originale** dell’articolo; non
  attribuire tutto a un solo marchio se i dati arrivano da aggregatori diversi.

- Supabase + Prisma — chiuso in specifica (verificare sempre la doc aggiornata Supabase/Prisma):
  - Default Tongue (consigliato per il corso): una sola variabile DATABASE_URL = connection
    string direct dal pannello Supabase (Database → URI, porta 5432, host db.<ref>.supabase.co).
    Un solo processo Render apre poche connessioni; prisma migrate dev / migrate deploy e il
    runtime usano la stessa URL. In schema.prisma resta solo url = env("DATABASE_URL").
  - Se si usa il pooler (transaction mode, es. porta 6543): DATABASE_URL = stringa pooling
    (come da Supabase, spesso con parametri consigliati per PgBouncer). Aggiungere in
    schema.prisma anche directUrl = env("DIRECT_URL") con la URI direct; su Render impostare
    entrambe le env. Le migrazioni useranno directUrl; l’app il pooler. Documentare in README e in
    server/.env.example.
  - Riferimento: documentazione Prisma con PostgreSQL su Supabase (siti prisma.io e supabase.com).

- Elenco fonti in risposta — chiuso: niente campo HTTP separato tipo `articlesUsed`; le fonti
  verificabili restano in `messages[].metadata.articles` (PF4, obiettivo 0.bis). Devono essere
  coerenti con il passo di pertinenza PF8, non un dump grezzo della sola cascata PS2.
- Cache server stessa data+query — chiuso: non prevista; si affida a PF3 (metadata) e ai refetch
  espliciti; meno complessità e niente stale data lato cache.
